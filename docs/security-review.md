# Security review — 2026-10-11

Actual deployed-frontend architecture in this checkout: client-only React/TypeScript on Vite; Netlify static hosting and a Netlify `quote` function using Resend. The repository also contains an undeployed Spring Boot/PostGIS/Cloudflare Tunnel scaffold. Live DNS, CDN configuration, and deployed provider state could not be inspected: hissus.com and the supplied reference/album URLs return proxy 403. This report does not assert that repository deployment settings are active.

## Dependency review

Read exact resolved versions from the pnpm lockfiles, ran `pnpm audit --json` for frontend and root, and fetched all 133 distinct GitHub Advisory Database pages referenced by the frontend baseline audit (all returned 200). Findings below include identifiers, affected/fixed ranges, original installed versions, current resolved versions, usage exposure, and remediation state. Advisory data is the package-registry audit response checked against the linked authoritative GitHub pages. Where no CVE is assigned, the GHSA is the identifier.

Frontend baseline audit metadata: 3 critical, 54 high, 78 moderate, 7 low (142 findings by the runner's counting). Final frontend audit: 0 critical, 1 high, 0 moderate, 0 low. Root baseline: 11 high, 2 moderate; final: 0 findings. These are audit counts, not distinct exploitable bugs. No forced major-version updates were performed: direct dependencies and transitive resolution refreshed inside the existing semver ranges; Playwright was added only as a dev dependency for regression tests. Build, TypeScript, locale and lint checks pass after the refresh.

The regenerated, policy-compliant lockfile resolves esbuild to 0.28.2 (the Windows serve advisory is fixed in >=0.28.1). pnpm 11’s active 24-hour release-age verification now passes. TanStack Query/core/devtools use mature 5.104.1, Zod 4.6.5, and ip-address 10.7.3; registry publication dates were checked. The project-local store is ignored, and only esbuild’s install script is explicitly allowed. No age, checksum, TLS, or signature verification was disabled.

Remaining finding:

## Application review and changes

- React renders text through the existing i18next setup; no `dangerouslySetInnerHTML` sinks found. The email handler escapes all user values, including the customer greeting previously interpolated without escaping. Subject CR/LF is removed.
- Server-side Zod validation now bounds field sizes, requires known products/cities for screen inquiries, supports international facility contacts with their own required name/company and inquiry subject fields (no screen city/product requirements), validates locale/types/email, rejects malformed JSON and a filled honeypot, limits raw body size to 16 KiB, applies an 8-second abort signal to each provider request, checks content type and restricts browser Origin. Honeypot and client disabled-submit controls are not security boundaries or DDoS protection.
- The handler never returns success when the team notification fails, including provider-returned errors. A failed optional customer confirmation is reported separately. Client responses are localized by error code; internal config/provider details are not sent to visitors. Eight function regressions exercise actual bundled handler/schema with a stub mail sender. No real messages were sent.
- `RESEND_API_KEY` and `QUOTE_RECIPIENT_EMAIL` remain server-side only. No public `VITE_*` secret was added. Environment variable names/presence were inspected; values were not printed. The local machine has no Resend key. No email delivery or domain authentication was verified.
- Marketing routes make no authenticated server requests. Zustand stores UI state, not JWTs. Login is an existing UI skeleton, not verified authentication. Axios's unused 401 redirect was corrected to preserve `/tw` without generating `/home/login`. No open external redirect was introduced.
- Netlify function rate-limit declaration: 5 requests per 60 seconds, aggregated by IP and domain. The installed provider `Config` type accepts it. Edge enforcement is pending deployment/provider support; local tests verify only the declaration, not live rate limiting.
- Netlify CSP limits scripts/connect/fonts to same origin, images to self/data and the exact `https://i.ytimg.com` thumbnail origin, frames to YouTube privacy-enhanced embeds, disables objects, restricts base/form origins, disallows framing, and upgrades insecure requests. Style inline allowance is retained for existing component/carousel inline positioning. Also prepares nosniff, DENY, strict-origin referrer policy, and camera/mic/geolocation denial. CSP was injected into local production HTTP responses and exercised in six bilingual pages, local images, and the configured embed URL: zero violations. External player network/content was stubbed, so full YouTube playback remains a deployment check. If `VITE_ASSET_BASE_URL` is set on the deployed site, add its exact trusted origin to img-src after testing; current local build uses same-origin assets.
- Fingerprinted `/assets/*` files have a prepared one-year immutable cache policy. No long cache policy is applied to index.html, forms or function responses (function uses no-store).

## Backend/infrastructure limits

No backend feature is needed for this static marketing redesign, and no database was introduced. Existing scaffold risks remain documented rather than silently presented as production protections: compose exposes 8080, defaults backend to dev, has a local database port override, references a tunnel secret without a complete mount, and has unpinned infrastructure images. Spring config disables CSRF globally and permits actuator endpoints, relying on network boundaries. Those controls are not verified in production and must be addressed before deploying authenticated APIs. Existing CORS targets localhost only. No backend/Java dependency audit, Docker image CVE scan, database startup, cookie/session/CSRF integration, or origin firewall test was performed in this frontend task; no running backend or credentials were required.
